Section 1

World Patterns

How Plasma owns identity, truth, evidence and representations.

1.1

Authoritative State / Derived Views

World pattern
Problem
Representations drift when each behaves as an independent truth.
Rule
Every piece of information has an owner; everything else is a projection, cached derivation or proposal.
Flow
WORLD ENTITY ├─ semantic facts → world graph ├─ exact shape → OCC BRep ├─ display → derived mesh └─ analysis → derived claim
1.2

Evidence → Claim → Belief

World pattern
Problem
Measured reality, simulations and AI interpretations have different certainty and provenance.
Rule
Observation is evidence, not state. Evidence creates claims with provenance and confidence before affecting world belief.
Flow
evidence ↓ interpretation ↓ claim + provenance ↓ confidence / conflict ↓ accepted belief
1.3

Projection, Not Duplication

World pattern
Problem
BIM, USD, Three.js, drawings and analysis models become unmanageable when they evolve independently.
Rule
External representations are projections of Plasma or typed proposals back into Plasma—not silent parallel truths.
Flow
PLASMA WORLD ├─→ Three.js projection ├─→ USD projection ├─→ analysis projection └─← typed import proposal
1.4

Stable Identity / Replaceable Representation

World pattern
Problem
Objects lose continuity when identity is tied to whichever geometric or visual form currently represents them.
Rule
Entity identity persists independently of whichever representation is currently used.
Flow
Tree_281 ├─ point proxy ├─ canopy envelope ├─ mesh ├─ splats └─ procedural model
Section 2

Change Patterns

How the world changes safely, incrementally and through stable contracts.

2.1

Propose → Validate → Commit

Change pattern
Problem
Humans, agents, imports and solvers all need to change the world without corrupting canonical state.
Rule
Nothing writes directly to canonical state. Every change first exists as a candidate patch.
Flow
human / agent / solver ↓ proposal ↓ candidate patch ↓ validation ↙ reject accept ↘ commit ↓ revision
2.2

Dependency-Driven Invalidation

Change pattern
Problem
World changes make some results stale, but recomputing everything destroys interactivity.
Rule
Derived results declare what they read and write; only downstream dependencies become dirty.
Flow
fact changes ↓ dependency edges ↓ affected derived values ↓ DIRTY ↓ lazy recomputation
2.3

Typed Operation Contract

Change pattern
Problem
Plasma needs to grow rapidly across languages, solvers and experimental implementations.
Rule
Capabilities are stable contracts; implementations are replaceable.
Flow
typed inputs ↓ operation ↓ typed outputs ↓ validation ↓ world patch

The implementation may be C++, TypeScript, Python, Z3, a GPU kernel, an LLM or an external solver.

2.4

Local Failure Containment

Change pattern
Problem
Plasma will combine heterogeneous and occasionally unreliable tools.
Rule
An operator failure invalidates only itself and its dependents; unrelated world state remains usable.
Flow
operator fails ↓ result = FAILED ↓ dependents unavailable ↓ unrelated state remains valid
Section 3

Scale Patterns

How Plasma remains interactive while worlds, candidate populations and analyses grow.

3.1

Progressive World Resolution

Scale pattern
Problem
Large worlds cannot become exact after every interaction without destroying responsiveness.
Rule
Resolve only what is needed, where it is needed, and as accurately as the current action or question requires.
Flow
ACTION ↓ cheap proxy response ↓ mark affected state dirty ↓ visible / relevant tiles first ↓ coarse → refined → exact ↓ background analysis

Example: drag a building with its current mesh immediately, then rebuild OCC geometry and dependent analyses after release.

3.2

Cheap Test Before Expensive Test

Scale pattern
Problem
Specialist simulation is wasted on worlds that already fail simple rules.
Rule
Order evaluation from cheapest, highest-elimination tests to expensive, high-fidelity tests.
Flow
scalar / bounding checks ↓ coarse geometry ↓ exact geometry ↓ specialist simulation
3.3

Coarse Reject / Fine Confirm

Scale pattern
Problem
Large design populations become computationally impossible if every candidate receives maximum fidelity.
Rule
Use cheap approximations to eliminate weak candidates; spend fidelity only on survivors.
Flow
10,000 candidates ↓ cheap 1,800 ↓ medium 300 ↓ detailed 30 ↓ exact 5
Section 4

Intelligence Patterns

How Plasma decides what matters, explores alternatives and uses human judgement efficiently.

4.1

Question-Driven Refinement

Intelligence pattern
Problem
A world model can become infinitely detailed without becoming more useful.
Rule
Refinement is driven by the decision or question being answered, not by a desire for total model completeness.
Flow
QUESTION ↓ required facts ↓ unresolved dependencies ↓ candidate operations ↓ refine relevant state
4.2

Fork → Evaluate → Select

Intelligence pattern
Problem
Generative exploration should not repeatedly mutate and damage one canonical world.
Rule
Alternatives branch from a common world, are evaluated independently, and selected results advance a lineage.
Flow
WORLD A ├─ A1 → evaluate ├─ A2 → evaluate └─ A3 → evaluate ↓ preserve / reject / select
4.3

Capability Frontier

Intelligence pattern
Problem
Agentic RAD can drift into speculative infrastructure instead of demonstrable product progress.
Rule
Develop the smallest valuable capability immediately beyond the verified frontier.
Flow
verified capability ↓ identify next gap ↓ build smallest slice ↓ test / verify ↓ commit ↓ frontier advances
4.4

Human Attention as a Scarce Resource

Intelligence pattern
Problem
Autonomous systems can overwhelm the architect with decisions, warnings and raw failures.
Rule
Escalate only when human judgment changes the outcome; package the decision with evidence and consequences.
Flow
issue ↓ can system resolve? ├─ yes → continue └─ no ↓ material human decision? ├─ no → defer └─ yes → concise escalation
North-star invariants: World owns state. LLMs propose operations. Deterministic systems validate. Exact geometry is authoritative where exact geometry exists. Representations are replaceable. Computation is dependency-aware. Complexity must be earned by demonstrated need.
