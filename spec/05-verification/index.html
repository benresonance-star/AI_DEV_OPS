PLASMA-VERIFY-001 · Canonical verification specification

Verification

What counts as proof that a capability became true without breaking existing verified behaviour.

CanonicalEvidence outranks confidence
Principle

Independent truth gate

The builder may propose success. Only independent verification can establish it.

Verification should use the cheapest strong evidence appropriate to the capability, escalating fidelity only as required.

Evidence hierarchy

Strongest cheap evidence first

  1. Compiler / type system
  2. Deterministic unit and integration tests
  3. Known deterministic test worlds
  4. Exact geometry validity
  5. Numerical tolerances and invariants
  6. Constraint satisfaction
  7. Regression tests
  8. Visual regression
  9. Performance benchmarks
  10. Specialist simulation comparison
  11. Human judgement where deterministic proof is unavailable

Test-world rule

Tiny worlds before realistic worlds

Important behaviour should be proven first using small deterministic test worlds with stable IDs and known expected outputs. Large realistic projects are valuable later, but they are poor first-line truth tests because too many variables move at once.

Example tiny world

A rectangular site, one rectangular building envelope, explicit 6 m setback, known height limit and expected exact area.

What it can prove

BRep validity, mesh derivation, setback pass/fail, dirty propagation, revision restore and unaffected-state preservation.

Verifier contract

PASS · FAIL · ESCALATE

PASS

Every required acceptance criterion is supported by sufficient evidence and no verified behaviour regressed.

FAIL

At least one criterion fails or evidence contradicts the claimed capability.

ESCALATE

The decision is materially architectural, ambiguous, unsafe or cannot be proven without human judgement.

The Verifier does not repair Builder code. It returns evidence.
Test integrity

Never move the goalposts to get green

Acceptance tests may change only with explicit evidence that the test is wrong or the authoritative specification has intentionally changed. A failing implementation is not evidence that the test should be weakened.
